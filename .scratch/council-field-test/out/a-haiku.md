### 1. Experience thesis

An 8/10 question card reads like a decision gate, not a form interruption. The question sits at 14px sans prose (68ch max), the options display as a tight group of toggle buttons below it (8px apart, 24px below the question), and focus lands on the first option on entry so a keyboard user reaches the answer without scanning. The submit button sits at the group's trailing edge and is always visible—never hidden on hover, never disabled until after submission—because the card interrupts a streaming run and must be dismissible. A second-glance reader sees: question, then options, then send. The card sits inside the transcript's content column (not full-width, not floating) so it reads as part of the conversation, scaled against the machinery (reasoning, tool rows) around it. One friction to avoid: option text that wraps inside a button, which breaks the visual grid; options are either single-line or stacked as a vertical list if space is too tight.

### 2. Three highest-value subjective calls

**Position: Options are toggle buttons with `aria-pressed`, never radio buttons or checkboxes.** The question mirrors opencode's terminal UI, where options are a radio group (one answer) that the user selects and confirms. A toggle with `aria-pressed` is the Blazor idiom that avoids double-submission: the button's state changes instantly, the submit action is separate, and a re-render does not reset the choice (by spec, open state lives in C#). *Counter:* radio buttons are the HTML semantic for "choose one", and porting opencode directly means radio semantics. A user notices the difference when they mis-click and expect to uncheck the button; with toggles, they must click another option to change their answer. *Response:* the app is a transcript reader, not a form. The toggle-plus-submit pattern fits the streaming context better than a radio-submit, and the contract already rules that open state is C# property, not DOM.

**Position: The submit button text matches the triggering question's verb, never generic "Submit".** When opencode says "Would you like to retry?", the button says "Retry", not "Submit". When it says "Select a provider", the button says "Confirm". *Counter:* a generic button is clearer to first-time users and is easier to test. A verb-matched button risks confusion if the question and button drift. *Response:* a user notices the drift when they read the button and question separately; a matched verb makes the card one unit at a glance. The question is in the brief, so the verb is known at render time.

**Position: Free-text answers are an optional textarea only when the question structure explicitly allows it (the `optional` flag or a question option count less than the total options listed).** If opencode says "choose from A, B, C or type your own", that is a list of toggle options plus a textarea below them. If it says "choose one: A, B, C", that textarea does not appear. *Counter:* a textarea is always available and maximally flexible; it handles unexpected user input and future question shapes. *Response:* a user notices the difference when they type into a card that does not expect free text and their input is silently ignored. The question structure is the contract; rendering a textarea on every card is noise and suggests a choice where none exists.

### 3. The one thing you would cut

Cut the feature that lets multiple options be selected at once (if such a feature is in the proposal). Opencode's question API always lists options as radio buttons or checkboxes in the terminal. If the app needs to support checkboxes (multiple answers), that is a new event type, not a variant of question cards. The contract says the answer goes back to the running process; accepting multiple answers when the process expects one creates silent failures. Keep the rule: one answer per card, always—and if a future opencode version emits a multi-choice question, that is a separate card design and belongs in a new ADR, not in this port.
